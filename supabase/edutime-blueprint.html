01

Actors & authority

There are three different, overlapping answers to "what are the user types" here — a Postgres role, an enum column, and one role that isn't a database row at all.

Layer one is Postgres itself. Every request arrives as one of three database roles: anon holds zero table privileges in public — confirmed by querying the grants directly, not assumed — so an unauthenticated request cannot read a single row, regardless of RLS. authenticated is every signed-in human, of any app role. service_role is the key held by pg_cron jobs and Edge Functions — never by a client.

Layer two is the user_role enum on public.users: student, class_rep, faculty_rep — three values, widened to four effective levels by class_rep_rank (primary / assistant), which a CHECK constraint makes structurally impossible to set on anyone who isn't a class_rep.

Layer three is Superadmin, which is not a row anywhere. It is synonymous with holding the service_role key. bootstrap_faculty_rep() — the function that installs the very first Faculty Rep — takes no p_acting_user parameter, because there is no users row to name as the actor. The audit trail it writes records actor_id = null, snapshot.actor = 'superadmin' by convention, not by reference.

There is no staff role in this platform, at all, and there never should be. A Class Rep or Faculty Rep is not a different kind of person from a Student — it is the same users row with role (and possibly class_rep_rank) changed. A Faculty Rep still carries a reg_number, a cohort_id, attends their own cohort's lectures, and shows up in cohort_unstreamed_members when their cohort splits. An earlier draft modelled Faculty Reps as Deans on staff addresses; that was corrected everywhere on 2026-08-24 (0032) — bootstrap_faculty_rep() only accepts a plain student, and nothing in the live schema treats a Faculty Rep as staff today. See §08 for the one stale comment that correction left behind, and why the write-up of the mistake itself stays in the docs.

Faculty Rep and Class Rep are two independent elevations from Student — not a ladder. Nothing promotes a Class Rep to Faculty Rep; bootstrap_faculty_rep() only accepts a plain student, called exclusively by whoever holds the service-role key.

02

Data model, by domain

Twenty tables, grouped by what they're actually for — not the order the migrations added them in.

Institution structure

faculties → departments

Both CASCADE downward. faculty_id is the unit Faculty Reps are scoped to everywhere else in the schema.

programmes → courses

programmes.code is globally unique — it's what registration-number parsing keys off. courses.semester_taught gates when a Class Rep may self-insert one.

buildings → rooms → venues

venues is polymorphic: CHECK constraints require a room_id for a physical venue and a meeting_link for an online one — never both, never neither.

People & identity

users

The one identity table. reg_number is nullable and unique — null until a roster row is claimed, never asserted directly.

student_roster

The institution's pre-declared truth: who exists, before anyone signs up. reg_number is UNIQUE and shape-checked by regex. claimed_by links it to a real account once claimed.

roster_audit_log

Append-only. Every claimed / takeover / dispute_resolved / reassigned event, keeping the trail even through ON DELETE SET NULL on the account it references.

user_recovery_email

A delivery channel, deliberately isolated from auth.users.email — carries no identity or auth weight of its own, just a 6-digit OTP and a throttle.

Cohorts

cohorts

Self-referencing: a stream is a cohorts row whose parent_cohort_id points at another cohorts row — see §03 for how the schema stops a stream ever drifting from its parent's programme/intake/pace.

cohort_join_requests

A student's request to join, decided by that cohort's Class Rep — decided_by is SET NULL if the decider's account is later deleted, but the decision itself survives.

Scheduling

events

One physical lecture occurrence. attendance_status ("will the lecturer show") is tracked completely separately from status ("is the lecture on the calendar at all").

event_cohorts

The junction that actually makes combined lectures work — an event can attach N cohorts, each with its own confirmation_status (pending / confirmed / declined / left) and its own course_id.

event_audit_log

changed_by_name is filled by a trigger at write time, so the trail survives the actor's account being deleted later — the ten functions that write here never had to handle that themselves.

events_current (view)

WHERE status IN ('scheduled','proposed') — the only two states worth putting on a calendar.

Governance & delivery

role_audit_log

Every promoted / demoted action, with a snapshot that includes identity_attested where relevant.

notifications

The single fan-out table — read by clients, read by pg_cron, and now carrying pushed_at for delivery tracking.

device_tokens / confirmation_nudges_sent

Two idempotency ledgers, one per background job — see §06.

03

What the schema enforces

The guarantees that don't live in application code at all — Postgres refuses the write, full stop.

Double-booking prevention is two EXCLUDE constraints, not a function. create_event can build all the pre-flight checking it wants; the actual guarantee is enforced at commit time by the GiST index underneath:

Both keyed on tstzrange(start_time, end_time) WITH && — an overlapping time range on the same key is a constraint violation, not an application error.
ConstraintGuards againstScope
events_no_venue_overlapTwo lectures in the same room/link at onceWHERE status IN (proposed, scheduled)
event_cohorts_no_self_overlapOne cohort double-booked across two different lecturesWHERE status IN (proposed, scheduled) AND confirmation_status ≠ 'left'

Structural rules, not validated input

cohorts_stream_inherits

Composite FK: (parent_cohort_id, programme_id, intake_year, pace) → (id, programme_id, intake_year, pace). A stream cannot exist with a programme/intake/pace that differs from its parent's — not because a function checks it, but because there is no row it could reference otherwise. enforce_cohort_stream_depth_trigger separately caps the hierarchy at exactly one level — no stream of a stream.

users_rank_only_for_class_rep

CHECK (class_rep_rank IS NULL OR role = 'class_rep') — a Student or Faculty Rep carrying a rank is not an application bug to catch, it's a row Postgres will not accept.

student_roster_reg_number_shape

A regex CHECK plus a UNIQUE constraint — the registration-number format and its uniqueness are schema facts, independent of whatever the claiming flow validates on the way in.

venues_physical_has_room / venues_online_has_link

A venue cannot be typed physical without a room_id, or online without a meeting_link — the two CHECKs make the invalid middle state unrepresentable.

04

Who can do what

Four layers, stacked — and the interesting part is what each layer can't do, which is why the next one exists.

L1 + L3 — grants (what RLS structurally can't restrict: columns)

authenticated holds table-level SELECT on almost every table — RLS narrows the rows, not the grant. Writes are the narrow part, and the real "no self-promotion" guarantee lives here, not in a trigger someone could forget to add:

Tableauthenticated may UPDATEauthenticated may NOT
usersfirst_name, last_name, middle_namerole, cohort_id, class_rep_rank, reg_number
notificationsread_atmessage, title, type, pushed_at
cohortscurrent_semester, pace (own cohort's class rep, via RLS)name (trigger-derived, not client-writable)
device_tokens— (no direct writes at all)every column — register_device_token() is the only writer

L2 — RLS: mostly "are you logged in", sometimes "is this your row"

Most reference-data policies (faculties, rooms, programmes…) are just auth.uid() IS NOT NULL — open to anyone signed in, which is fine because L1 already stopped anon cold. Personal or scoped data narrows further: device_tokens_read_own is user_id = auth.uid(); event_cohorts_read_if_attached and two siblings all delegate to one helper, user_can_see_event(event_id), rather than repeating the join three times.

L4 — the real API surface

Of 58 functions in public, the overwhelming majority are SECURITY DEFINER, and the pattern if p_acting_user is distinct from auth.uid() then raise exception opens nearly every client-facing one — the function accepts an actor id as an argument only so it can immediately refuse to trust it as anything other than a self-check. Authority itself is re-derived inside the function body by joining users/event_cohorts live, never taken from a client-asserted role.

Five functions no human can call at all — granted to service_role only, invisible to both anon and authenticated: bootstrap_faculty_rep request_password_recovery claim_pending_pushes invoke_push_dispatch send_confirmation_nudges. The first is Superadmin's only door in; the rest are internal machinery for background jobs and Edge Functions — reachable only by whoever holds the service-role key. See §08 for why request_password_recovery's lock reads stricter than it is.

05

Scheduling a lecture, end to end

One client call, and everything it sets in motion.

create_event(...) takes a JSON array of {cohort_id, course_id} attachments — one call handles a single-cohort lecture and a multi-cohort combined lecture identically. For a recurring series, the horizon is least(p_until, the EARLIEST term end among every attached cohort) via term_bounds() — bounded by whichever cohort's semester ends soonest, not by the initiator's alone.

Every occurrence is inserted in one transaction. If any occurrence's time range collides with an existing venue booking or cohort commitment, the EXCLUDE constraints from §03 reject it — and because it's one transaction, the entire series aborts, not just the clashing date. create_event catches that and names every offending date back to the caller, rather than leaving a partially-materialized series.

A combined lecture starts proposed, not scheduled — each non-initiating cohort's Class Rep independently confirm_event_cohort / decline_event_cohort / leave_event_cohorts their attachment. A recurring combined series gets one confirmation for the whole run (confirm_recurrence_group) rather than one per occurrence — the per-occurrence version was what kept this feature out of scope until it was rebuilt.

Whether the lecture is on the calendar and whether the lecturer will actually show are two separate facts — events.status vs. events.attendance_status. confirm_attendance re-derives the caller's standing at call time — a live join across event_cohorts ⋈ users filtered to role = 'class_rep' and an attachment that hasn't been declined or left — rather than trusting a cached role. Any attached cohort's rep may confirm, not only the initiator's.

Every one of these mutations ends by calling notify_cohort_members(), which inserts one notifications row per matching user — see §06 for where that row goes next.

06

Notification → push

One table, two independent cron jobs reading it on two different clocks, for two different reasons.

Two different idempotency shapes, on purpose. A reminder tier can independently re-fire for the same event five times (24h / 12h / 5h / 1h / 30m out), so it needs a real ledger keyed on (event, tier). A push is 1:1 with the notification it came from, so a single notifications.pushed_at column is the entire mechanism — stamped the instant a row is claimed, even for a user with zero registered devices, so a device-less user's rows don't get rejoined against device_tokens forever.

device_tokens.token is the primary key, not (user_id, token) — a resold or handed-down phone gives a different student the same FCM registration token, and register_device_token() deletes the previous owner's claim before installing the new one.

Edge Functions (Deno, supabase/functions/)

recovery-request

Unauthenticated entry point. Calls request_password_recovery with the service-role key, mints a GoTrue recovery link against the account's synthetic address, delivers via _shared/axene.ts. Same generic response whether the account exists or not.

recovery-email-setup

Self-service: sends the 6-digit OTP set_recovery_email generates, via Axene.

dispatch-push

Invoked only by invoke_push_dispatch(). Claims a batch, signs a JWT with the Firebase service-account key, exchanges it for an OAuth token, sends each push, deletes on UNREGISTERED only.

_shared/

axene.ts, fcm.ts, cors.ts — both mail and push wrappers share one rule: an unset API key logs the payload instead of sending, so local dev stays green with nothing configured.

Triggers (14 on public, 1 on auth.users)

on_auth_user_created

→ handle_new_auth_user. Only trusts raw_app_meta_data for an OAuth signup; a reg-number signup's synthetic address never leaks into public.users.email.

set_cohort_name_trigger

Derives cohorts.name from cohort_display_name() — never client-writable directly.

enforce_cohort_stream_depth_trigger

Caps the stream hierarchy at one level, alongside the composite FK from §03.

enforce_max_class_reps_trigger

Caps a cohort at two reps (primary + assistant).

guard_users_self_update / guard_notifications_update / guard_cohorts_rep_update

The trigger-level half of the column-grant story in §04 — belt and suspenders on the same guarantee.

*_broadcast_trigger

Fan out events / event_cohorts changes into private realtime.messages channels, gated by their own RLS policy.

08

Where the docs and the database disagree

Findings from reading pg_catalog directly instead of the changelog, sorted into what actually needed fixing versus what only reads that way.

Fixed

user_can_see_event()'s own comment was stale — corrected in 0035. It named "faculty reps" as an example of a NULL-cohort_id account, which was true when written but stopped being true the moment 0032's domain-model correction gave every Faculty Rep a real cohort_id, same as anyone else. The function's behavior was never wrong — it fails closed on NULL regardless of whose account it is — only the comment was teaching the old model. Landed as a comment-only CREATE OR REPLACE, the same shape 0032 used to fix guard_users_self_update's stale error message: no behavior change, ACL preserved, verified against the applied function and the full pgTAP suite.

There is no live functionality anywhere in this schema that treats a Faculty Rep as staff — that model was fully replaced by 0032, confirmed by grepping the entire tree for staff, @chuka.ac.ke, and "no registration number": every remaining hit is either unrelated (the staff-vs-student email-address shape distinction reg_number_from_email still correctly makes — a real, separate concern) or the write-up of the correction itself. bootstrap_faculty_rep() only accepts a plain student; every Faculty Rep in seed.sql carries a reg_number, a cohort_id, and an oauth roster claim, identical in shape to any other student row. TODO.md §3.5 and TECHNICAL_DISCOVERY.md §10 keep the write-up of the mistake on purpose — it's the reason a future migration is unlikely to reintroduce it, not a lingering trace of it.

Correct as built, commonly misread

request_password_recovery is granted to service_role only — anon holds no EXECUTE on it, and cannot call it directly. Read on its own, that looks like the unauthenticated "forgot password" flow shouldn't be reachable at all. It's reachable a layer up: the client calls the public recovery-request Edge Function with the ordinary anon/publishable key, exactly like any other Edge Function call, and that function — not the client — escalates to the service-role key before calling the RPC. The privilege boundary is between the Edge Function and the database, never between the client and the Edge Function. Tightening this further wouldn't harden it; a forgot-password flow that required being logged in already couldn't do its job, and this one already returns a byte-identical response whichever of "account doesn't exist / is OAuth-only / has no recovery address / is inside its cooldown" is true, plus a per-account throttle. This is the hardened version, not a gap in it. Unrelated to the Faculty Rep correction above — different function, different migration (0031 vs 0032), no shared mechanism; it only sat in the same section of the first draft of this document, which is what made it look connected.
